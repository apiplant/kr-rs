# Known Issues & Potential Problems

Only work still to do lives here (open items, things to watch, accepted limits). Numbers are stable (other docs cite them); new items get the next number. When something is fixed, move it to `RESOLVED_ISSUES.md` with the commit.

## Open
126. **Single-threaded control plane: one core** — *ADR-004, ADR-005, ADR-050*
    The API server, kubelet, controllers, scheduler, Service proxy (userspace mode) and DNS share one executor thread (plus the fsync helper, the offload workers of ADR-052 and, with `KR_PROXY=nft`, the kernel for Services). Measured (`kr-apiserver/tests/throughput.rs`, release, in process, 2000 pods): GET 51,000/s, create 16,000/s, status merge-patch 10,000/s, delete 40,000/s, list of 2000 pods 3,200/s (0.3 ms), labelSelector list over 2000 pods 270/s (3.7 ms); the handler is a small part of a request over the network, where TLS records and HTTP parsing bring a warm request to about 0.5 ms, i.e. roughly 2,000 requests/s per core before the handler. That serves the clusters kr is meant for (a server plus tens of nodes; the stall watchdog and `/metrics` show when it does not) but not the thousands of requests per second a large cluster's watchers and kubelets generate, where k3s spreads over all cores. CPU-heavy work (big lists, audit bodies, image unpack) already leaves the loop. The next step, if a deployment needs it, is not threads in this process (the state is `Rc`/`RefCell` throughout) but front-end worker processes that terminate TLS and parse HTTP (the larger part of the per-request cost) and pass requests to the main process over socketpairs, authenticating clients themselves and forwarding the identity: it needs streaming (watch, logs, exec, upgrades) designed first, so it is not started.
127. **Durability limits of in-process writers and watches** — *ADR-024*
    Writes by the controllers and the server's own kubelet are not awaited for durability: a background task flushes them every second, so a crash can lose up to about one second of them (they re-derive their state from the API). Watch events are delivered when written, not when durable, a deliberate deviation from etcd. Revisit if a controller ever keeps state that cannot be re-derived.
130. **Images: rootless keeps flattened rootfs; no manual image removal** — *ADR-017, ADR-056*
    As real root images are stored as layers shared between images (RESOLVED 271); a rootless store still unpacks one flattened rootfs per image (whiteout devices and `trusted.` xattrs), so rootless images duplicate shared layers. The kubelet now removes unused images when the store's filesystem is over 85% full (RESOLVED 277, ADR-057); there is still no command to remove one by hand (`crictl rmi`), the GC waits while any container directory lacks an image record (containers of the previous release, `kr run`), images pulled before the layered store stay flattened until pulled again, and blobs of images installed before this release that are not named by a manifest are never removed.
131. **seccomp: the default is a deny-list; no AppArmor or SELinux** — *ADR-018, ADR-055*
    `seccompProfile` `RuntimeDefault`/`Unconfined`/`Localhost` are honoured (RESOLVED 270). The default filter denies a list of dangerous syscalls (and anything newer than the build knows) instead of allowing a known set as containerd's `RuntimeDefault` does: an allow-list would break workloads that run unconfined under upstream's defaults. `appArmorProfile` and `seLinuxOptions` are not applied.
132. **Pod and Service CIDRs: IPv4 /16 only, set before the first start** — *ADR-053*
    `KR_POD_CIDR` / `KR_SERVICE_CIDR` accept any `A.B.0.0/16` (RESOLVED 261), so at most 256 nodes and 254 pods per node; other prefix lengths are refused, the IPv6 networks (`fd00:88::/32`, `fd00:96::/112`) are fixed, an agent must be started with the same values as the server (nothing checks it), and changing them on an existing cluster is unsupported (as in k3s).
133. **Service proxy: the kernel datapath is opt-in** — *ADR-022, ADR-036, ADR-054*
    With `KR_PROXY=nft` (root) Services are DNAT rules in the kernel (RESOLVED 262): client addresses are kept, connections survive a kubelet restart. It is not the default yet: it is verified in network namespaces (`tools/test/nft-proxy.sh`) but not on a real cluster with a CNI. The userspace proxy (default, and always rootless) still has its limits: lower throughput and higher latency, every Service connection ends with the kubelet process, `externalTrafficPolicy: Local` and source IP preservation depend on the splice. The kernel datapath: linear rules (hundreds of Services are fine), no SCTP.
136. **CSI: volume statistics are filesystem-level; expansion errors are not reported** — *ADR-041*
    `kubelet_volume_stats_*` and the `volume` entries of `/stats/summary` are served (RESOLVED 268), from `statfs` of the directory a claim is mounted from: for a CSI volume that is its own filesystem, for a local-path or hostPath PV it is the host filesystem the directory lives on (upstream reports the same), and the driver's `NodeGetVolumeStats` is not used. Only the node of this server's kubelet is reachable through `nodes/<n>/proxy`; an agent is scraped on its port 10250. `NodeExpandVolume` is only driven for volumes mounted by a pod running on the node, never for offline expansion, and not for raw block volumes. Expansion is not retried with backoff or reported as a `NodeResizeError` condition on the claim; failures are only logged once.
137. **CSI: block volumes and inline ephemeral volumes** — *ADR-041*
    `volumeMode: Block`, inline `csi:` ephemeral volumes and generic ephemeral volumes backed by CSI are not supported; only the first PV access mode is sent to the driver. (The scheduler's NodeVolumeLimits filter exists: RESOLVED 259.)
143. **API priority and fairness: width of mutating requests** — *ADR-033*
    Width is estimated from the stored object count (one seat per 100, max 10); a mutating request takes one seat, where upstream adds seats for the write phase and for the watchers a write fans out to. Borrowing never revokes a lender's seats (as upstream: a lender whose requests arrive while a borrower holds them runs over its limit briefly). Seats, queue length, borrowed seats and admitted/refused counters per priority level are on `/metrics` (RESOLVED 265); the response headers carry only the flow schema and priority level UIDs.
144. **Pod network families: changes and IPv6-only hosts** — *ADR-032, ADR-034*
    Changing `KR_POD_FAMILIES` needs every agent restarted and pods from before are lost (a CIDR/family change on a live cluster is unsupported, as in k3s); IPv6-only pods need host IPv6 for NAT66 (bridge setup fails otherwise); the host-gw backend routes IPv6 pod subnets only on an IPv6 underlay; the registry mirror, image pulls and DNS upstreams use whatever the host resolver offers. (Stale host-gw IPv6 routes are removed now: RESOLVED 266.)
146. **Server-side apply still differs from structured-merge-diff in corners** — *ADR-021, ADR-028*
    The built-in list/map table is name based (not generated from the OpenAPI schema), so uncommon fields can differ from upstream (unsure: `secretRef`/`configMapRef` `LocalObjectReference` atomicity, `envFrom`, `volumeClaimTemplates`; all treated as atomic lists / granular structs). Empty keyed/set lists own nothing (conflict detection differs only for a field that is empty), and CRD list-map-key defaults are not applied before computing keys. (`i:` index elements, which upstream produces only for lists without a declared type, do not arise: unspecified lists are atomic.) No known workload is affected; a conformance comparison against a real API server is the way to find more.
165. **`NetworkPolicy` is bypassed through Service ClusterIPs with the userspace proxy** — *ADR-022, ADR-049, ADR-054* — **security; fixed with `KR_PROXY=nft`**
    (keep the existing text and add:) The built-in enforcement (ADR-049) filters only forwarded traffic (the `forward` hooks); the userspace Service proxy terminates the connection on the node and re-opens it from the host (`output` hook, host to pod), which is always allowed (as upstream allows host to pod), so a policy still does not apply to ClusterIP/NodePort traffic. The proxy was not changed: binding the outgoing connections to the client pod IP (`IP_TRANSPARENT`/`IP_FREEBIND`) also needs a policy route / return path so the backend's reply reaches kr and not the client directly, which is more than a bounded change. Fix with the nftables DNAT datapath of ADR-045 (traffic is then forwarded with the client's source, so these tables apply unchanged).

### Missing compared with k3s
154. **No Helm controller** — *missing compared with k3s*
    ADR-043. The `<data dir>/manifests` directory applies plain YAML/JSON, but there is no `HelmChart` custom resource or Helm controller (`k3s` ships one); charts must be rendered with `helm template` into a manifest file. Applied objects are never deleted when their file goes away (the `kr.io/manifest-file` annotation records the origin so you can find and delete them).
156. **CA rotation is not implemented** — *missing compared with k3s*
    ADR-043. `kr pki rotate` replaces the leaf certificates but the cluster CA (10 years) cannot be rotated: the CA hash is pinned in `node-token`/`server-token` and in every agent's bootstrap, `ca.pem` is read as a single certificate, `kube-root-ca.crt` and the kubeconfigs embed it, and servers/agents load trust roots only at start. The two-step design is: (1) add a new CA to `ca.pem` as a bundle (old first, so signing keeps using `ca.key`), restart all servers, then agents, republish `kube-root-ca.crt` and the admin kubeconfig; (2) switch signing to the new CA key, re-issue every leaf (`kr pki rotate`) and node certificate (agents re-bootstrap), recompute the token hashes; (3) drop the old CA from the bundle. Steps need `kr` to parse a multi-certificate `ca.pem` in `pki::load_ca`, to accept a bundle in the TLS roots everywhere, and a new token scheme. Until then a CA compromise means rebuilding the cluster from a snapshot with a new CA by hand.
    Checked against k3s: `k3s certificate rotate-ca` exists (with integrity checks, `--force`, token reconfiguration for self-signed CAs, non-disruptive when the same root is kept). Not parity.

### NVIDIA GPU support: open items (ADR-038, ADR-039)
Related: #138 (topology), #139 (unhealthy devices), #140 (`PodResources`), #141 (`Allocate` batching), #142 (exec'd processes).
160. **MIG, time-slicing and MPS are untested** — *ADR-038*
    Not implemented or run here (needs NVIDIA hardware). Plan: (1) time-slicing: configure the GPU Operator with `devicePlugin.config` (`sharing.timeSlicing.resources: [{name: nvidia.com/gpu, replicas: 4}]`); expect `capacity`/`allocatable` of `nvidia.com/gpu` = 4 x GPUs, ids like `GPU-uuid::0`; four pods each requesting 1 must all start and `nvidia-smi -L` must work in each; the plugin returns CDI names `nvidia.com/gpu=<uuid>`, check the replica id suffix is stripped by the plugin and that `choose`/allocation treat the ids as opaque strings (they do). (2) MIG: set `mig.strategy=mixed` (resources `nvidia.com/mig-1g.5gb`, ...) and `single` (renamed `nvidia.com/gpu`); create instances with `nvidia-smi mig` or the mig-manager; verify the pod sees exactly one MIG device (`nvidia-smi -L`), that CDI specs for MIG devices (`nvidia.com/gpu=MIG-...`) resolve, and that caps device nodes (`/dev/nvidia-caps/*`) appear in the container. (3) MPS: `sharing.mps.resources`; the plugin starts the MPS daemon and returns a mount of `/run/nvidia/mps` plus env `CUDA_MPS_PIPE_DIRECTORY`; check that the mount is shared (mount propagation, ADR-041) between the daemon pod and workload pods, that pods use the same IPC namespace (`hostIPC` or the daemon's), and that the daemon's `nvidia-cuda-mps-control` sees the clients. For every case also test GetPreferredAllocation (#138) with replicas and unhealthy handling (#139): a replica of an unhealthy GPU must all turn unhealthy.
164. **GPU: live verification still pending for `poststop` and a kubelet restart** — *ADR-039*
    Verified live on 2026-11-12 (RTX 4090, root server): non-root pod with `runtimeClassName: nvidia` (groups 1000 and 985, `nvidia-smi -L`, `/dev/dri/card0` opened), pod requesting `nvidia.com/gpu: 1`, GPU Operator pods running, the device filter (#162, resolved). Still to do: a CDI spec with a `poststop` hook on the root server (the server must see it: `/etc/cdi` or `KR_CDI_DIRS` in its environment) and check it runs when the pod is deleted; restart the server while a long-running GPU pod is up and check it keeps running and its devices stay allocated; the new PodResources and unhealthy-device code (#166).

### Found while working through the issues (2026-11-12)
166. **PodResources and the unhealthy-device eviction have no live verification** — *ADR-038*
    Encoders and handlers are unit tested only. To do on a GPU node: run the dcgm-exporter with its pod-mapping feature (`--kubernetes`, socket mounted at `/var/lib/kubelet/pod-resources`) and confirm the GPU metrics carry `pod`/`namespace`/`container`; `grpcurl -plaintext -unix /var/lib/kubelet/pod-resources/kubelet.sock v1.PodResourcesLister/List`; fake an unhealthy GPU (plugin with a failing health check, or `nvidia-smi -i 0 -pm 0` plus an XID injection) and check the pod fails with reason `Evicted` within about 10 s. Unknown-yet: the socket mode (created by `unix_listen`, same as the plugin socket, root only), and the missing `Watch`/`GetDynamicResources` calls of newer upstream versions.
167. **Unhealthy-device eviction: bare pods are deleted, no restart in place** — *ADR-038*
    After the grace period (`KR_DEVICE_UNHEALTHY_GRACE`, default 30 s) the kubelet asks the eviction API to remove the pod (RESOLVED 252: a PodDisruptionBudget can hold it back for `KR_DEVICE_UNHEALTHY_PDB_WAIT`, default 600 s). This goes beyond upstream (which only lowers the node's allocatable and leaves the pod running; the user chose to keep it). `restartPolicy` plays no part (a Deployment or Job replaces the pod, a bare pod is gone). Not yet exercised on a real unhealthy GPU.

174. **ServiceLB limits** — *ADR-042*
    Checked against k3s's `servicelb.go` and klipper-lb: k3s publishes the nodes' ExternalIPs when any exist, else the InternalIPs (kr the same), sets neither `ipMode` nor ingress `ports`, ignores `loadBalancerIP`, detects no port clash (the second Service's pod stays Pending on the host port; kr gives only the older Service an ingress) and passes `loadBalancerSourceRanges` to klipper as an allow-list in front of a drop (kr: RESOLVED 282). What remains: all Services are re-evaluated on every Service, Node or EndpointSlice event (cost grows with the number of LoadBalancer Services times nodes); the load-balancer and external addresses are served only on the node that holds the address (a node listens on the ingress IPs that are its own); in userspace mode an external IP that is not a local address is not served; `externalTrafficPolicy: Local` publishes only nodes with a ready endpoint but the proxy on other nodes still forwards the NodePort. Source ranges apply to the load-balancer addresses, not to the cluster IP, external IPs or node ports, and never to clients on the node itself.
175. **`registries.yaml` gaps** — *ADR-027, ADR-044*
    Mirror endpoints cannot carry a path prefix (`https://host/v2/prefix`), `rewrite` supports a regex subset only (no `{n,m}`, lazy quantifiers or lookaround), only the first match is replaced, `*` works as the default for `mirrors` and, now, for `configs` (RESOLVED 304; specific entries win, as in k3s). A blob download that fails after a mirror answered the manifest is not retried on the next endpoint. A registry that needs a client certificate only for some paths or an RSA client key is unsupported (kr-crypto signs with P-256/Ed25519 only, and its TLS client sends a single configured certificate).
176. **Air-gap import: no zstd, no pod-level image names, full copy** — *ADR-044*
    `.tar.zst` archives and zstd layers are refused because kr-archive has no zstd decoder. Archives are first extracted to `<store>/import.tmp-*` (needs free disk of one archive size) and the start-up directory is `<KR_ROOT>/agent/images` even when `kr agent --data` points elsewhere. A multi-arch OCI archive without the node's platform imports nothing for that entry silently. Import never replaces an existing ref's image unseen by id, it just repoints refs.
    Checked against k3s: its own airgap archives are `.tar.zst` (placed in `agent/images`), so kr cannot import the official k3s airgap tarballs. Not parity.
177. **No overlap period for the service-account key; no hot reload** — *missing compared with k3s*
    ADR-043. Restarting after `kr pki rotate` matches k3s (`k3s certificate rotate` also needs the service stopped), but k3s rotates the service-account issuer key with an overlap: the new key file keeps the old key appended so existing tokens stay valid, then servers restart and agents and pods are untouched. kr's verifier accepts only one key: `kr pki rotate --service-account-key` is refused in HA (`sa.key` must be identical on every server and join copies it only once) and on a single server it invalidates all existing tokens. Also, `kr pki rotate` on a server whose `admin.kubeconfig` is gone issues a new kubeconfig for port 6443 unless `--port` is given.
178. **Backup is a point-in-time copy of one server's files, with caveats** — *limitation*
    ADR-043, ADR-024, ADR-026. The archive is built by reading the data dir files, on the event loop when scheduled (a very large store stalls the server for the duration of the read). In HA the Raft commit index is persisted only when the term or vote changes, so `--committed-only` can lag far behind; by default every entry in the local log is included, which on a follower may contain a few entries that were never committed. Archives are uncompressed and unencrypted (they hold `ca.key`, `sa.key` and tokens: file mode 0600 is the only protection). Restore always yields a single-server data dir; the old HA servers' `raft/` and `server-id` are not carried over, and agents must be able to reach the new server under the old address (or be re-pointed). Pod state on nodes is not part of a backup. The `kr` crate has no unit tests (`test = false`); `snapshot.rs`, `rotate.rs` and `manifests.rs` are covered by `tools/test/tooling.sh` only (the archive code is unit-tested in kr-store).
179. **Upgrade script is only dry-run tested** — *unverified*
    ADR-043. `tools/upgrade/kr-upgrade.sh` was exercised with `--dry-run` and `bash -n` only; it has not been run on real nodes. It treats a node as healthy as soon as `Ready=True`, which is already true right after the restart of a node that was Ready before (the cordon holds until uncordon), and it picks `kr-server` over `kr-agent` by `systemctl is-enabled`, which `--restart` overrides.

### Found while working through the issues, wave 2 (2026-11-12)
180. **Audit: streams and long-running requests only log ResponseStarted** — *ADR-046*. Watches, exec/attach/portforward and upgraded connections emit `stage: ResponseStarted` when the response begins; there is no `ResponseComplete` at stream end and no `requestObject` for them. Upstream emits both.
181. **Audit: webhook-only and internal writes are not audited** — *ADR-046*. Events are produced in the HTTP transport, so writes by in-process controllers and the in-process kubelet (client::InProcess), and requests forwarded between HA servers (audited by the receiving server only), are not logged. Forwarded reads/writes are logged where the client connected.
182. **Audit: pod-security audit annotations are recomputed from the request body on POST only** — *ADR-029, ADR-046*. Spec updates of existing pods and PUT/PATCH of workloads do not add `audit-violations` annotations, and the annotation is added even when admission later rejected the request for another reason. Upstream annotates after the decision, also on updates.
183. **Audit: no `auditID` propagation, no `Audit-ID` response header, no webhook/dynamic backends, no batching modes** — *ADR-046*. Only the log backend exists; `--audit-log-format`, `--audit-log-maxage`, `--audit-webhook-*` are not implemented. Backups are named `audit-<UTC time>.log` (lumberjack's local time and `.gz` compression are not used).
184. **Audit: cost of identity resolution** — *ADR-046*. When the policy has no `users`/`userGroups` rules and the level is None, the request is skipped without authenticating. Otherwise the bearer token is verified a second time by the audit hook (a third time with impersonation). Caching the transport's identity would remove it.
185. **Pod Security version pinning is partial** — *ADR-029, ADR-046*. Only seccomp, restricted capabilities and hostProcess are version dependent; other rule changes (e.g. the 1.25 baseline sysctl and AppArmor list changes, restricted volume types before 1.0.x) are evaluated as latest. Exemptions by `runtimeClassName` need the pod spec to name it (RuntimeClass defaulting is not consulted). The user exemption needs one extra authentication per write when `exemptions.usernames` is set.
188. **secrets-encrypt reencrypt/disable are offline, single-server only** — *missing compared with k3s*
ADR-047. `kr secrets-encrypt reencrypt|disable` rewrite `db/` and need the server stopped (a live server would overwrite the result; no lock detects this). In an HA cluster they refuse: old ciphertext (and old keys' ciphertext) stays in the Raft log until compaction, and there is no online re-encryption. Workaround: no-op update each Secret with kubectl, then wait for a Raft snapshot, before dropping an old key.
    Checked against k3s: `k3s secrets-encrypt rotate-keys` runs on a live server and re-encrypts by itself (restarts in sequence on HA) and `status` reports stage and per-server hashes. Not parity.
189. **Key rotation needs a restart and is not propagated in HA** — *missing compared with k3s*
ADR-047. The server reads the config only at start. `rotate-key` edits the local file; in HA the new file must be copied to every server (same key set) before restarting any of them, otherwise a server cannot read what another wrote and refuses to apply the record (exit). The join flow copies the file only at first join (SHARED glue in `join_secrets`/`join_cluster`, `crates/kr/src/server.rs`). No online key-sync RPC.
192. **Nonce limit and no automatic rotation** — *known limit*
ADR-047. Nonces are random 96-bit: the per-key limit is 2^32 encryptions (every Secret write, including each re-encrypt). Rotate (`rotate-key` + `reencrypt`) well before; there is no counter, so nothing warns when it is approached.
195. **`kr snapshot` of an encrypted store keeps ciphertext, store digests ignore encryption** — *info*
`Store::from_files` and raw tools load without a codec, so values stay ciphertext and `image()` re-emits them unchanged (restoring works). `ApiServer::store_digest` hashes `Store::plain_image()` (nonces differ per server). Tools reading values must install the codec.
196. **HorizontalPodAutoscaler: `status.krHistory` is a kr extension** — *ADR-048*
    The controller supports Resource, ContainerResource, Pods, Object and External metrics (RESOLVED 239, 241). `custom.metrics.k8s.io` and `external.metrics.k8s.io` exist only when an adapter is installed and registered as an APIService, as in k3s, which ships metrics-server alone (checked against the packaged-components page); the adapter path is tested with a stand-in client, not a real adapter. The history for the stabilization windows is stored in `status.krHistory`, visible in `kubectl get hpa -o yaml` (upstream keeps it in memory only); an object copied to another cluster carries it along.
197. **Pod metrics need a delegated cgroup and only cover running containers** — *ADR-048, ADR-007*
    Container CPU/memory come from the container's cgroup v2 files, so without a delegated cgroup (`Config::cgroups` false, e.g. rootless without `systemd-run --user -p Delegate=yes`) `kubectl top pod` is empty while `kubectl top node` still works. Terminated containers, the pause sandbox and init containers that finished are not reported; ephemeral storage, network and filesystem stats are not collected (`/stats/summary` has no `fs`, `network`, `rlimit`; `usageNanoCores` is 0 there, use the cumulative counter).
198. **Metrics API: sampling limits** — *ADR-048*
    Values appear after the second scrape (about 20 s after start, 15 s refresh); scrapes of nodes are sequential with a 10 s timeout each, so a cluster with many unreachable nodes refreshes slowly; every API server of an HA cluster scrapes on its own (no leader election, N times the load) and keeps its own cache, so two servers can briefly disagree. Entries older than 2 minutes disappear. The resource is advertised through the built-in resource table, so generic features see it (`kubectl api-resources` lists it) but it is not stored, there is no `APIService v1beta1.metrics.k8s.io` object (`kubectl get apiservices` does not list it) and no `watch`, `Table` output or OpenAPI schema for it.
199. **Other kubelet metrics endpoints are missing** — *ADR-048*
    `/metrics/cadvisor` (container network/fs/CPU throttling series, used by Prometheus and Grafana dashboards), `/metrics` (kubelet internals) and `/metrics/probes` are not served; `kubelet_volume_stats_*` (the CSI `Csi::volume_stats()` in `crates/kr-kubelet/src/csi.rs` already computes the numbers) is not exposed, so PVC usage alerts have no source (related to #136).
201. **NetworkPolicy does not filter traffic to or from the node itself** — *ADR-049, ADR-022*
    Rules sit on the `forward` hooks (inet) and the bridge `forward` hook, so packets delivered to the node (pod to node IP, pod to the kube-dns/Service ClusterIPs which the node serves locally, pod to the API server on the node) and packets from the node (probes, proxy) are never filtered. Consequences: an Egress default-deny does not block DNS or Service traffic (upstream would block them unless allowed), and `hostNetwork` pods are not selectable and not matched as peers. Host-to-pod being always allowed matches upstream.
    Checked against kube-router (k3s's NetworkPolicy controller): it hooks `INPUT`, `FORWARD` and `OUTPUT` (`KUBE-ROUTER-INPUT/FORWARD/OUTPUT`), so k3s does filter traffic to and from the node. This is a real difference, not parity.
202. **Policy tables are replaced as a whole on every change** — *ADR-049*
    Peers that are single pod addresses and share their ports are now one nft set per chain and port list (RESOLVED 278), so a chain no longer has a rule per peer IP and port. Still: the table is rebuilt and replaced atomically whenever pods or policies change (pod churn re-programs it, at most every 500 ms), set elements are not added or removed incrementally, ipBlock prefixes and groups of fewer than 3 peers stay plain rules, and the IPv6 set path is only unit tested (the kernel test covers IPv4).
203. **NetworkPolicy: a new pod is open until the next pass (about half a second)** — *ADR-049*
    The controller now watches pods, namespaces and policies (RESOLVED 255) and recomputes within ~0.5 s of a change, so the window is a fraction of a second instead of up to 3 s. A pod's first packets can still leave before its chain exists: the rules need the pod's IP, which reaches the API only with its first status report. Closing it fully needs the kubelet to install the pod's chain from the address it allocates, before the container starts (a pre-start hook). Untested against the kernel like the rest of the built-in enforcement (#205).
204. **Built-in enforcement limits** — *ADR-049*
    `endPort` ranges and named ports are supported; SCTP is matched by protocol/port only. Protocol and port matches use `meta l4proto` and the transport-header payload, which the kernel resolves past IPv6 extension headers (checked in the code, not by a test with extension headers); a non-first fragment has no transport header, so it matches no port rule and is dropped where a port is required. Denied packets are not logged and policies get no `status`: upstream's v1 API has neither, so these are not gaps. The bridge table needs `nf_tables_bridge` (a failure to program it is logged, routed traffic is still enforced, but same-node pod-to-pod would be open). Switching `KR_NETWORK_POLICY` or the CNI needs a kubelet restart.
205. **NetworkPolicy enforcement: the bridge table is untested against the kernel** — *ADR-049*
    The `inet` forward table is verified in a real kernel (RESOLVED 264: ingress allow/deny by peer and port, default deny, egress, and with the nftables Service datapath in front). Not covered: the `bridge` table for same-node bridged pod traffic (the test pods are routed, not bridged), `ipBlock` with `except`, named ports and IPv6 peers (computed offline, unit tested only), and a run of the kubelet's controller end to end on a cluster whose CNI is the built-in bridge.
206. **CSR approval validation is approximate** — *ADR-042*
    `kube-apiserver-client` CSRs for privileged groups other than `system:masters` are not restricted. Violations return 422 (`Invalid`) rather than upstream's field-level errors, and the `status` subresource now requires an approved, not denied/failed request, an immutable `certificate` and a PEM `CERTIFICATE` chain and the first certificate's public key must equal the request's (the issuer is not checked against the signer). `ssa`/apply requests to `approval` are not validated (only `update_ex` callers: PUT and PATCH).

207. **Node authorizer: list/watch scoping is partial** — *ADR-023*
    A kubelet identity may list/watch `volumeattachments` only with `fieldSelector=spec.nodeName=<its node>` (or one name that is its own), and may not list/watch `persistentvolumes` except one it uses (kr's kubelet only does single gets). `csidrivers`, `csinodes` and CSR reads stay open to nodes as upstream's `system:node` role grants them. A node may create CSRs of any signer (as upstream's role); kr's CSR controller only auto-approves the kubelet signers for the requesting node (ADR-042).

208. **Offload facility: not every CPU-bound step uses it yet** — *ADR-050, ADR-052*
    The facility exists (RESOLVED 237, 238) with two classes: short API jobs and long image jobs. Users: big list renderings, audit bodies, image unpack/verify/fsync. Candidates that still run on the loop: snapshot images and hashing (#212), file writes (#223), TLS handshakes (#209: a worker would need the private key and session state, so that is a design question), the unpack of `kr ctr import` (a CLI, nobody to starve) and the first layer decompression of `kr ctr` commands. Limits: a job's input and output are copied through a socket (4 MB takes about 3 ms of the loop), so tiny work does not pay; each class has 2 workers and the 17th concurrent caller runs inline; each worker is a fork of the server taken at start-up, so it holds a copy-on-write image of the process at that time.

209. **TLS handshakes still run on the loop** — *ADR-050, #208*
    Tickets now survive restarts and work across HA servers (RESOLVED 234), so the reconnect storm after a restart is mostly resumed handshakes (0.9 ms for both sides, mutual TLS) instead of full ones (3.3 ms, 2.7 ms with the CA key table); only clients without a ticket (first start, ticket older than an hour, a client certificate that changed) pay for a full handshake, still inline on the event loop. What remains is the helper of #208 for bursts of full handshakes, and the variable-base multiplications of a full handshake: the ECDH with a P-256 peer share (X25519, preferred by kr, Go and OpenSSL clients, is ~190 us) and `u2 * Q` for leaf certificate keys.

210. **Very large lists: copy, selection scan and first parse remain on the loop** — *ADR-050, ADR-052*
    Big Table, metadata-only and defaulted CRD lists and big audit bodies are rendered in workers (RESOLVED 237). Still on the loop: the selection scan of `labelSelector`/`fieldSelector` lists (the byte pre-filter plus parsing the survivors, 2.5-5 ms per 3000 pods), the splice of a plain list (0.35 ms per 3000 pods) and the cost of copying the items to and the rendering back from a worker (about 3 ms for 4 MB). The parsed-object cache holds up to 24 MB of JSON as trees (about 3-4x that in memory) and is dropped by halves when full. A list of hundreds of thousands of objects is still one allocation and one response body of that size.

212. **Hashing and compression in the store and snapshots block the loop** — *ADR-050, #208*
    Store digest/`plain_image` for snapshots (#195), `kr snapshot` and Raft snapshot creation, the Raft log segment checksums, bcrypt-like token checks and the secret encryption codec (AEAD per Secret write, re-encrypt in #188) are inline. Candidates: take the Raft/store snapshot image in the helper (copy-on-write fork of the process, as Redis does, is the simplest correct approach for a consistent image), and batch AEAD for re-encryption.
213. **Raft and API serving share one thread: causes of stalls remain** — *ADR-004, ADR-050, #126, #208*
    The watchdog, heartbeat priority and configurable election timeout are in (RESOLVED 213a). What remains is removing the stalls themselves (#209–#212)  The stall counters are now served (RESOLVED 248).

215. **Other synchronous disk work remains on the event loop** — *ADR-050, #208*
    The device-plugin checkpoint is now written without fsync on the loop and flushed in a worker (RESOLVED 272); the rootless infra file (once per start) and the CNI/IPAM/state files are still written with fsync inline; the start-up sweep (cgroups, recorded processes, `remove_unclaimed_dirs`) now yields between steps and after each removed directory (RESOLVED 275), but each single step (one cgroup tree walk, one pod directory removal) is still synchronous. Use `KR_STALL_WARN_MS` and the "last phase" label of the stall log to find which one matters on a given machine; the fix is the helper facility of #208 or moving the fsync to the durable-commit helper process (ADR-024).

220. **TLS resumption: what ADR-051 leaves out** — *ADR-051*
    TLS 1.2 connections (client side only, opt-in) do not resume. The API servers share ticket keys derived from `sa.key` (RESOLVED 234); agents (their kubelet endpoint) and servers whose `sa.key` differs use random per-process keys, so those tickets die with the process. There is no 0-RTT and no revocation other than the one-hour ticket lifetime: a client certificate whose CA was replaced keeps its resumed sessions until the tickets expire (up to an hour), and replacing `sa.key` invalidates all tickets. Servers whose clocks differ by more than one hour cannot open each other's tickets. `KR_TLS_RESUMPTION=off` disables it.

223. **A `write()` to a log file can block the event loop for seconds** — *ADR-050, #208, #212*
    Not seen again in the stall log. The audit log is now written by the one-second flusher only (a request flushes inline just when 4 MB are buffered), and an audit write that takes 100 ms or more prints "audit log write ... blocked the event loop". Still synchronous on the loop: the store log append (`Store::write_out`, before the fsync goes to the helper), compaction (`Store::rewrite_log` writes a snapshot and fsyncs four times inline) and pod log files. Linux throttles a buffered writer in `balance_dirty_pages` under write-back pressure. Fix if it shows up: hand these writes to the helper of #208 (the fsync helper process of ADR-024 could take them), or bound dirty data with `sync_file_range`.
    Measured (`kr-store/tests/compact_timing.rs`, ignored, release, local NVMe): `rewrite_log` of a 9.2 MB image (3000 pods of 3 KB) takes 21 ms inline, of which `image()` is 3.9 ms; the rest is the write and the four fsyncs. Below the stall threshold on this disk; a slow disk or write-back pressure would multiply the fsync part, which is why the fsyncs, not the image, are the part to hand to the helper if a compaction ever shows in the stall report.

226. **Start-up stalls that remain after the fixes of this session (up to ~190 ms)** — *ADR-050, #208, #213*
    Seen once per restart: the first status patch of a Failed pod (`cal/client`, 152 ms for one `report_status`), the availability probe's `PATCH /apis/apiregistration.k8s.io/v1/apiservices/v3.projectcalico.org/status` (144 ms, while the extension API is still down), and the first attempt of a failing container start. Use the stall report (phase, request, spawn site) and the `kubelet: slow ...` lines to find the cost of each; none was investigated further.
    Later run (adoption of 62 pods, no recreation): the longest stalls are `report_status` of the first pod patched after a restart (162 ms for `cal/other`, 40-76 ms for the next pods). It is not the merge patch itself: `tests/patch_timing.rs` (ignored; `cargo test --release -p kr-apiserver --test patch_timing -- --ignored --nocapture`) measures a pod status patch at 70-100 us, first and later alike. The `slow report_status` timer is wall time across the awaits, so it also counts other tasks that ran meanwhile; the stall report's single-poll duration is the better number. Candidates: fan-out of the resulting watch event to the many pod watchers at start-up, and the kubelet's own status computation (`stamp_conditions`, `keep_foreign_conditions`), `sync_pod` of `gpu-operator/gpu-feature-discovery` (107-129 ms) and `tigera-operator` (75 ms): container starts, whose blocking wait is fixed (RESOLVED, container shim await); the CDI specs are only 17 KB, so parsing them is not the cost.
    Latest restart (concurrent sandbox starts, 57 pods adopted): one stall of 116 ms in the connection task of `PUT /apis/nfd.k8s-sigs.io/v1alpha1/namespaces/gpu-operator/nodefeatures/arch`, last phase `http: response built` (after the handler and the audit, so it is in the response write or the next read); the connection loop now labels `http: handled`, `http: send response` and `http: next request` to tell them apart. Also `report_status` 147 ms (first patch after a restart), `sync_pod` 97 ms (gpu-operator); three `start_sandbox` of 1.1-1.2 s each while started together (Calico serialises, so the batch still finishes sooner than one after the other).
    Next restart (with the new labels): no event-loop stall at all. What remains is latency, not blocking: `report_status` 152 ms for the first pod patched (wall time across awaits), `sync_pod` 77 ms, `refresh_volumes` 43 ms, and the aggregated `projectcalico.org/v3` lists at 323-383 ms (#225). The 116 ms NFD stall did not recur, so its cause stays unknown; if it returns the new labels will place it.

    Aggregated `projectcalico.org/v3` requests, measured on the live cluster after the pooled clients: 50-86 ms steady (`networkpolicies`, `globalnetworkpolicies`, `ippools`, three runs each), so the 300-560 ms lines were connection set-up. The first requests after a restart still take 320-380 ms (cold connection to the extension server and its own warm-up); the remainder of the steady figure is Calico's API server.

# Nice to have later (beyond k3s)
Ideas that build on what kr already has and that k3s does not offer. None is planned; each is sized (S: days, M: a week or two, L: more) and says what it would reuse. "Not checked" means I believe k3s lacks it but did not verify. Do these only after the open items above.

291. **Seccomp profile recorder** — *M, not checked against k3s*
    Run a pod with a log-only filter (`SECCOMP_RET_LOG`, kr already compiles the BPF itself, ADR-055), collect the syscalls from the audit/kernel log or a `seccomp_unotify` listener, and write an OCI `Localhost` profile that allows exactly those. Upstream needs the security-profiles-operator for this; k3s ships nothing. Reuses `kr_runtime::seccomp`, the `Localhost` profile path (`spec::seccomp_dir`) and the pod exec path. Needs: a `kr seccomp record <pod>` command and a pod annotation `kr.io/seccomp-record`.
292. **FQDN egress policy** — *M, not checked against k3s*
    Allow egress to `*.example.com` in a NetworkPolicy extension. kr runs its own cluster DNS (`kr-net::dnsserver`), so the answers for allowed names can feed an nft set of peer addresses with the answer TTL (set support exists: RESOLVED 278). kube-router (k3s) has no FQDN rules. Needs: an annotation or a small CRD for the name list, the DNS server publishing answers to the kubelet's netpol controller, and expiry of elements. Risk: clients that bypass cluster DNS.
293. **Image signature verification at pull** — *M, not checked against k3s*
    Verify cosign signatures (ECDSA P-256 over the manifest digest, keyless is out of scope) before an image is used, with a cluster-wide policy file (`image-policy.yaml`: registry/repository pattern, public keys, `enforce`/`warn`). `kr-crypto` already verifies P-256 and Ed25519 and the pull path knows the manifest digest. k3s has no admission or pull-time verification of its own. Needs: signature fetch (`.sig` tag convention), a policy matcher, a pod event on refusal.
294. **Point-in-time object history and restore** — *M*
    The store keeps revisions until compaction (ADR-024). `kr history pods/ns/name` could list the retained revisions with their diffs and `kr restore --revision N` write one back, which etcd and kine only offer through manual `etcdctl` or SQL. Needs: a retention knob for revisions of selected resources (compaction currently drops them), and a diff in `kr-fmt`.
295. **Snapshot without a stall (copy-on-write fork)** — *M*
    `kr snapshot`, scheduled backups and Raft snapshot creation hash and copy the store on the event loop (#178, #212). A forked child holds a consistent copy-on-write image and writes the archive while the parent keeps serving, as Redis does. k3s with etcd streams a snapshot but has no such guarantee for SQLite. Needs: a fork helper that is safe in a single-threaded `no_std` process (the offload facility, ADR-052, already forks workers) and care with the disk write bandwidth.
296. **Online secrets re-encryption and hot key reload** — *M*
    k3s rotates keys on a live server but needs restarts in sequence on HA (docs.k3s.io, secrets-encrypt). kr could re-encrypt in the background in small batches through the offload workers and reload `encryption-config.json` on a signal or file change, replicated to every server through the Raft log so no restart and no copy step is needed (#188, #189). Needs: an internal key-sync record in the log, a progress status in `kr secrets-encrypt status`.
297. **Hot reload of the audit policy and PodSecurity configuration** — *S*
    Upstream and k3s read both at start-up (RESOLVED 281). kr's own server could watch the files and swap the compiled policy atomically. Needs: a validated parse before the swap and a log line on failure that keeps the old policy.
298. **`kr why <pod>`: an explanation of a Pending or failing pod** — *S*
    One command that gathers what the scheduler, the kubelet and the events already know (unschedulable reasons per node, missing PVC or image, sandbox errors, device shortage, quota) and prints a short diagnosis. Reuses scheduler filter results (they exist as event messages), pod status and recent events. k3s has `kubectl describe` only.
299. **Upgrade planner: stored objects and removed APIs** — *S*
    `kr upgrade plan` lists stored objects whose API version or fields the target kr release no longer serves, and CRDs that would break, before the binary is replaced (#179 covers the script). The store can enumerate everything; the check needs the target release's resource table. k3s has nothing built in.
300. **PSI-based node pressure** — *S*
    Use `/proc/pressure/{memory,cpu,io}` (PSI) for the eviction loop and the node conditions next to MemAvailable, so a node that stalls on memory reclaim is tainted before it runs out. Upstream has PSI metrics only; k3s defaults do not use them. Needs: thresholds as environment variables and a node condition.
301. **Ephemeral-storage limits through filesystem project quotas** — *M*
    `ephemeral-storage` limits are enforced upstream by periodic `du` unless the quota-monitoring gate is on (needs XFS/ext4 project quota); k3s leaves it to the defaults. With real root kr could set a project quota per pod directory and per container upper layer at creation and read usage back cheaply, and refuse the write at the limit instead of evicting afterwards. Needs: `FS_IOC_FSSETXATTR` in kr-sys and a mount with `prjquota`; fall back to the current behaviour when absent.
302. **Built-in GPU status and sharing without the operator** — *M*
    The kubelet already discovers devices, runs the device filter and reads PodResources (ADR-038, ADR-039). A `kr gpu` command and node labels from NVML-free sysfs data (model, memory, MIG state, driver version) plus time-slicing as a kubelet setting would cover single-node setups without the GPU Operator (which k3s needs for this). Needs: hardware to test MIG and time-slicing (#160); keep the operator path working.
303. **Server upgrade without dropping client connections** — *L*
    With the front-end TLS workers of #126 a new server binary could take over the listening sockets and the worker processes while the old one drains, so `kubectl` watches and exec sessions survive a binary swap (#134 shows the sessions end with the process today; k3s restarts the service). Needs: the worker split first, a socket-handoff protocol, and a story for Raft leadership during the swap.

311. **KMS provider or envelope keys for secrets encryption** — *L, was parity (#190)*
    k3s and kr both keep the raw key in a file next to the data. A KMS-style provider (a unix-socket plugin as in upstream's KMS v2, or a key wrapped by a passphrase or TPM at start-up) would let the data dir be stolen without the key. Needs: the socket protocol, caching of the data key, a start-up path that works when the provider is down (refuse, never fall back to plaintext).
312. **Snapshot controller and CRDs bundled** — *M, was parity (#153)*
    Neither k3s nor kr ships VolumeSnapshot support. Bundling the external snapshot controller manifests (off by default) and testing the CSI node path against Longhorn would make `VolumeSnapshot` work on a fresh cluster. Needs: the manifests in the `manifests` directory mechanism, a test with a real driver (#136, #137).
313. **Kubelet serving certificates through CSRs, and ClusterTrustBundles** — *M, was parity (#173)*
    Both kr's and k3s's kubelets take their serving certificate from the join flow. With `serverTLSBootstrap` the kubelet would request a serving certificate through the CSR flow kr already implements (RESOLVED 273) and renew it before expiry without a restart; `ClusterTrustBundle` (beta, off by default upstream until 1.37) would give workloads a CA bundle object. Needs: the kubelet CSR client, rotation, an approver rule for `kubernetes.io/kubelet-serving`.
314. **Keep decrypted values out of memory dumps** — *M, was parity (#191)*
    kube-apiserver and kr hold decrypted Secrets in memory. kr could keep Secret values encrypted in the store map and watch history and decrypt on use (cost: an AEAD per read), and mark the pages `MADV_DONTDUMP`. Needs: a benchmark of the read path, care with the parsed-object cache (ADR-052).
315. **Restart containers when the GPU driver changes** — *S, was parity (#163)*
    Running containers keep the driver libraries they started with. The plan in the old #163 (a hash of each allocation's resolved CDI edits, a 30 s re-check, a `DriverChanged` event and an opt-in annotation `kr.io/restart-on-driver-change`) would automate the restart. k3s and upstream leave it to the user. Needs: GPU hardware to test, the resize-restart path.
316. **Built-in custom-metrics adapter for HPA** — *L, was parity (#196)*
    HPA custom and external metrics need an adapter in k3s and kr alike. kr's own `/metrics` scrape and pod metrics could back a small `custom.metrics.k8s.io` for the metrics kr already has (event-loop, per-pod cgroup counters), so a basic setup needs no Prometheus adapter. Needs: the APIService wiring and a metric catalogue; not a replacement for prometheus-adapter.
317. **Certificate rotation without a restart** — *M, was parity (#177)*
    Rotating certificates needs a service restart in k3s and kr. The API and Raft TLS configurations could be reloaded on a signal or file change (the ticket keys derive from `sa.key`, ADR-051, and survive). Needs: swapping the TLS config under live connections, the same for the Raft transport; pods are unaffected today.

# Accepted limitations (by design, or not planned for now)
227. **Starting a container forks the kubelet process twice (~8 ms of the loop)** — *accepted, not planned* (ADR-050)
    Two `clone3` forks of the server (page tables of ~200 MB resident: 3-5 ms each) plus `store.create_container`, `apply_fs_group` and the pod-log setup. The wait for the container setup no longer blocks. Decision: far below the stall threshold and never named by a stall report, while the fix (a fork-server helper holding a serialised spec and the passed descriptors, or spawning `kr shim` with the spec on a pipe) rewrites the central container-start path. Revisit only if a stall report names a container start; a failing start such as `default/bm` could then check cheap preconditions (volumes, mounts) before creating the container directories.

151. **No Ingress controller** — *missing compared with k3s*
    k3s ships Traefik. kr stores `Ingress`/`IngressClass` objects but runs no controller; an ingress controller must be installed (it needs `LoadBalancer` or host ports, see the issue above).
    Decision (ADR-045): not bundled by design; install it as a normal workload.
11. **aarch64 path is only partly exercised**
    Cross-built binaries run under qemu-user (`tools/test/aarch64.sh`); `kr ctr`/kubelet/apiserver paths (namespaces, cgroups, clone3, mounts) do not work there and need a real aarch64 host. No CI job yet.
53. **Binary size** — *watch*
    The single binary (server, agent, runtime, TLS/crypto, CRDs, webhooks, aggregation, protobuf tables) is 3.10 MB on x86_64 (measured 2026-11-01; was 2.87 MB on 2026-10-27, and 2.32 MB on aarch64 then; it was ~1.8 MB when the 2 MB agent budget in PLAN.md was set, which is now exceeded). Measure before adding large features; avoid `{:?}` on large types, and keep `opt-level = "z"` + LTO + strip.
60. **P-256 scalar multiplication is slow** — *watch*
    Now a constant-time fixed 4-bit window (masked table scan): ~0.5 ms sign, ~0.95 ms verify (was 0.75 / 1.4 ms), dudect |t| 0.4. Fast enough for the API server's handshake rate so far; revisit if that changes.
97. **HA (kr-raft, ADR-026) design limits**
    - Membership changes are one server at a time (single-server changes, the safe protocol); a server whose IP changes while running needs a restart.
    - Linearizable reads rely on a leader lease (a quorum heard within half an election timeout); it assumes bounded clock drift between servers. Reads with an explicit `resourceVersion`, and watches, are served from the local applied state without a barrier.
    - Snapshots are sent whole in one message (512 MB frame limit). Plan: chunked InstallSnapshot if images grow.
115. **Leftovers of resolved items (not planned)**
    - CRD conversion: objects written earlier keep their stored version (a `StorageVersionMigration` rewrites them on request); for a CRD with a conversion webhook, server-side apply through a non-storage version is recorded as an Update (the converted write is a PUT).
    - Rootless: the host cannot reach pod IPs directly (use port-forward or the API server's pod proxy).
    - Memory: with 4 KB pods the 32 MiB history budget keeps about 4,000 events (watch the `410 Expired` rate); per-pod server growth (about 120 KB at 100 pods) has no per-category breakdown.

125. **API TLS handshake ~40% slower than k3s**
    `kr-crypto` TLS 1.3 handshake ~2.3 ms vs k3s ~1.6 ms (crypto optimized for memory/size). Request handling on warm connections is faster (0.5 ms vs 1.1 ms). Optimize handshake if needed.

123. **File bind-mounts of a deleted inode fail (`errno 2`)** — *kernel limit, not a kr bug*
    A hostPath file that is a bind mount whose source inode was unlinked (e.g. `findmnt` shows `[/src.txt//deleted]`, link count 0) fails with `volume mount: errno 2`. Confirmed 2026-11-11: plain `mount --bind` of such a file fails the same way (`move_mount() failed: No such file or directory`), while a bind mount with an intact source works through kr. Docker produces this when the host file is replaced after the container started; recreate the mount (restart the container).

### Terminal Ctrl-C of `kr server` killed the pods (fixed, untested live)
Sandboxes (`kr pause`) stayed in the server's process group, so a Ctrl-C in the terminal sent them SIGINT and the restarted kubelet found nothing to adopt (`adopted 0 pods`), leaving `Failed`/`SandboxFailed` ghost pods (a rejected or failed-setup pod now reports no `containerStatuses`, so `kubectl` shows its reason instead of `ContainerCreating`). ADR-036 was only tested with `kill -9`. `clear_pdeathsig` now also calls `setsid` in survive mode. Needs a live check: Ctrl-C the server and see that the next start adopts the pods. Pods started by the previous binary still die once.

### CSI node side (ADR-041): works with Longhorn; limits
Verified with Longhorn 1.x on a root kubelet: provisioning, attach, Stage/Publish, a pod writing and a second pod reading the data after detach/reattach, and deletion through the external provisioner. Not supported: block volumes, inline `csi:` ephemeral volumes, node-side expansion, volume stats; only the first PV access mode is sent. CSI needs a root kubelet. The state dir is `/var/lib/kubelet` (`KR_KUBELET_DIR`) and must differ from the kubelet root (`cfg.root`). Longhorn's deployer detects the kubelet root from a host process named `kubelet` or `k3s server`, so install it with `--set csi.kubeletRootDir=/var/lib/kubelet`.

### Longhorn disks must support FIEMAP (ext4/XFS), not tmpfs
Not a kr bug. A Longhorn replica exits at once on a tmpfs data path (`FS_IOC_FIEMAP` returns ENOTSUP), while the node still reports the disk Ready. For throwaway tests use an ext4 image on tmpfs: `truncate -s 4G /tmp/lh.img && mkfs.ext4 -q -F /tmp/lh.img && sudo mount -o loop /tmp/lh.img /tmp/lh-disk`, and add `/tmp/lh-disk` as the node disk.

### Pods keep the mount setup of the binary that started them
Containers survive a kubelet restart (ADR-036), so after an upgrade that changes how mounts are made (e.g. `mountPropagation`, ADR-041) a running pod keeps the old behaviour until it is recreated. Delete the affected pods (Longhorn: instance-manager, csi-plugin, manager).

### Calico (tigera-operator, VXLAN, `NetworkPolicy`) works with an external-CNI server start
Verified 2026-11-12 on the shared cluster: start the server with `KR_CNI_CONF_DIR=/etc/cni/net.d KR_CNI_BIN_DIR=/opt/cni/bin` (both directories must exist); without a CNI config kr keeps its bridge, so the restart changes nothing until Calico writes its conflist. Install the CRDs first (`helm template calico-crds projectcalico/crd.projectcalico.org.v1 | kubectl apply --server-side -f -`), then `helm install calico projectcalico/tigera-operator -f values.yaml` (pool `10.244.0.0/16`, VXLAN, BGP disabled; keep it off `10.88.0.0/16`). Results: typha, calico-node, kube-controllers, API server, goldmane and whisker Ready; pods get Calico IPs; pod-to-pod, DNS and egress work; 30 replicas ready in 18 s with distinct IPs; 780 Service requests (300 sequential, 480 concurrent) without a failure; `NetworkPolicy` blocks direct pod-IP traffic from a pod that is not allowed.
- **`NetworkPolicy` is not enforced for traffic through a Service ClusterIP**: see #165. Direct pod-IP traffic is enforced.
- **A host process listening on a wildcard port blocks Services on that port.** The proxy binds `ClusterIP:port`, which fails with `EADDRINUSE` while something owns `0.0.0.0:port` (here a non-kr process on `:80`). A Service port with no ready endpoint is no longer bound, so a host-network pod such as typha (`:5473`) can bind it first.
- Pods that existed before the switch keep their `10.88.0.x` addresses and bridge; they and Calico pods reach each other through the host.
- Helm charts that contain custom resources need the cluster to serve `/openapi/v2` as protobuf (now done), and the operator's `istios` CRD needs `type: integer` with `x-kubernetes-int-or-string` accepted (now done).
- `kubectl get endpoints` shows only NAME and AGE (no ENDPOINTS column).
